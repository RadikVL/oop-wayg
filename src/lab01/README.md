Вариант №4 — банковская система. Из предложенных сущностей (`BankAccount`,
`Transaction`, `Client`, `Credit`, `Deposit`) я выбрал **`BankAccount`**,
потому что у него:

- понятный набор атрибутов (номер, владелец, баланс, ставка),
- естественные ограничения (баланс ≥ 0, ставка от 0 до 100, номер счёта —

- понятные бизнес-операции (положить, снять, начислить проценты),
- логическое состояние (счёт активен / заблокирован),
- естественный критерий равенства (по номеру счёта).

То есть на этой сущности удобно показать всё, что требуется в работе.

## Ответы на 5 вопросов с практики

### 1. Что является сущностью?

Сущность — **банковский счёт**. Это реальный объект предметной области:
у него есть номер, есть владелец, есть остаток денег и процентная ставка,
с ним можно совершать операции и его можно блокировать. Это не действие
(транзакция — это уже действие), а именно объект.

### 2. Какие у него атрибуты?

| Атрибут          | Что хранит                   | Тип       | Закрытое поле     |
| ---------------- | ---------------------------- | --------- | ----------------- |
| account_number   | номер счёта (20 цифр)        | str       | `_account_number` |
| holder_name      | ФИО владельца                | str       | `_holder_name`    |
| balance          | текущий остаток на счёте     | float     | `_balance`        |
| interest_rate    | процентная ставка (% годовых)| float     | `_interest_rate`  |
| is_active        | активен ли счёт              | bool      | `_is_active`      |

Плюс **атрибут класса** `bank_name` — он один на все счета и поэтому
вынесен на уровень класса, а не экземпляра.

### 3. Какие инварианты?

Правила, которые должны быть верны **всегда**:

- номер счёта — непустая строка из 20 цифр,
- ФИО — непустая строка из букв (плюс пробелы и дефисы),
- баланс ≥ 0,
- 0 ≤ процентная ставка ≤ 100,
- сумма пополнения и сумма снятия — положительные числа,
- снять можно не больше, чем есть на счёте,
- на заблокированном счёте никакие денежные операции не работают.

Все эти проверки собраны в одном месте — в `validate.py` — и вызываются
и из конструктора, и из сеттеров. За счёт этого валидация не дублируется.

### 4. Что значит «равенство»?

Два счёта **равны, если у них совпадает номер счёта**. ФИО владельца,
баланс и ставка могут быть какими угодно — это всё равно один и тот же
счёт (например, в системе «свежий» снимок счёта и тот же счёт через час
с другим балансом — это один счёт).

Реализовано в `__eq__` — сравниваем только `_account_number`.

### 5. Есть ли состояние?

Да. У счёта два состояния: **активен** и **заблокирован**, переключение —
методами `activate()` / `deactivate()`.

Поведение от состояния зависит так:

- активный счёт: `deposit`, `withdraw`, `apply_interest` работают;
- заблокированный счёт: те же методы кидают `RuntimeError`.

Это и есть «поведение, зависящее от состояния», требуемое в задании на 5.

## Сценарии демонстрации

В `demo.py` четыре блока вывода:

**Сценарий 1. Создание счёта и базовые операции.**
Создаём счёт, печатаем через `print` (`__str__`) и `repr`, кладём
500 ₽, снимаем 200 ₽, начисляем 5 % — баланс растёт по правилам.

**Сценарий 2. Состояние счёта.**
Блокируем счёт через `deactivate()` — все три денежные операции
кидают `RuntimeError`. Разблокируем через `activate()` — операции
снова работают.

**Сценарий 3. Валидация (сеттеры и конструктор).**
Меняем ставку и имя через сеттеры — корректные значения принимаются,
некорректные отбиваются `ValueError`. Дополнительно — список из пяти
вариантов «битых» аргументов конструктора, каждый ловится своей
валидацией. Также показано, что `withdraw` не даёт уйти в минус.

**Бонус. Сравнение и атрибут класса.**
Создаём два счёта с одинаковым номером и разным содержимым — они равны
(`__eq__` смотрит только на номер). Создаём счёт с другим номером —
не равен. Печатаем `bank_name` через класс и через экземпляр.
